# Skill Lifecycle Manager

一套贯穿 skill 生老病死的元认知闭环。它不干具体业务，只做五件事：**触发判断 → 申请建立 → 分层 → 脚本化迁移 → 使用后迭代**。每一步的关键是「**先申请、后执行**」——绝不自动落地，人类始终是裁决者。

## 何时用

- 一次复杂/多步任务收尾时，自动反思「这次有没有值得固化的东西」。
- 用户问「这个要不要做成 skill」「能不能自动化」。
- 一个 skill 刚被使用过，想判断它是否需要迭代。

## 何时不用

- 单步任务、单次查询、简单问答——**静默，不打扰**（避免「推销员」式打扰，见铁律 3）。

## 铁律（违反即失效）

1. **先申请，后执行**：建立、迁移、迭代，都是「向用户申请」，用户明确同意后才落盘。绝不自动创建/覆盖/删除 skill。
2. **判断靠可判定信号，不靠感觉**：触发判断依赖可量化的事实（token、纠正次数、复用次数），不是「我觉得这个值得」。
3. **静默阈值**：简单任务（单次翻译/查询/一句话）绝不触发反思。只有多步骤、高成本、有复用潜力的任务才开启。宁可漏报，不可烦人。
4. **测量 > 反思**：判断「skill 是否需要迭代」必须用事实（使用中的报错、用户纠正、或 `skill-evaluator` 的 A/B 数据），不是自我感觉良好。

## 阶段一：完成对话时的触发判断

一次任务收尾时，检查三个维度，**命中任一**即进入阶段二申请：

| 维度 | 可判定信号 | 阈值示例 |
|---|---|---|
| 成本痛点 | token 消耗、用户对同一件事的纠正次数 | 纠正 ≥ 3 次，或同一动作做了多轮 |
| 知识盲区 | 是否依赖本地私有脚本、专有环境、个人约定 | 涉及本机路径/脚本/凭据/个人工作流 |
| 重复模式 | 与现有 skill 或历史对话的重合度 | 连续两次类似任务，或与某 skill 高度重合 |

**静默阈值**（先于三维度判断）：若本次是单步、一次性、无复用潜力的任务，直接不触发，不输出任何反思。

## 阶段二：申请建立

命中触发条件后，向用户输出结构化申请，**等同意，不擅自生成**：

> 🚨 检测到本次任务符合【成本痛点：你已就 X 纠正了我 3 次】。建议把这套逻辑固化为 skill。是否现在生成草案？（回复「同意」生成，回复「拒绝」继续）

用户拒绝 → 停止，不纠缠。用户同意 → 进入阶段三。

## 阶段三：拆分层级

生成草案前，先定位这个 skill 该落在哪一层（四层金字塔）：

1. **系统原语层**——读写文件、运行命令、1+1 这类 agent 自带能力 → **不可做成 skill**。若触发条件命中的是这类，直接告诉用户「这是 agent 本来就有的，不需要做成 skill」。
2. **原子能力层**——单职责、高复用、输入输出明确（如「脱敏扫描」）。
3. **业务流转层**——把多个原子能力按顺序串起来解决具体场景（如「打包→安检→推送」）。
4. **策略编排层**——含条件分支、决策门控、动态调度（如「安检不过绝不推送」）。

判定口诀：**「模型已内化吗？」是 → 不做；「是单动作还是组合？」单 → 原子，组合 → 业务流转；「有门控/条件分支吗？」有 → 策略编排。**

**跨 skill 脚本引用规则**：写 SKILL.md 时若需引用**不属于本目录**的脚本/资产，不能写成相对本目录的路径（如「运行 `scripts/` 下的 judge 脚本」这种写法）——那会让执行者在本 skill 目录里找不到文件、触发静态体检「坏引用」。正确做法：按**协作 skill 名称**引用（如「运行 skill-evaluator 提供的 judge 脚本」），并说明来源；若确要内置，先复制进本目录再写相对路径。写完必须跑静态体检确认无坏引用。

## 阶段四：脚本化迁移（先预测 token，再判断，再申请）

建 skill 时，主动判断「哪些内容该下沉到本地脚本」。判断顺序：**先量化 token 消耗，再定性质，最后申请**。

### 4.1 预测 token 消耗（三层计费，不靠感觉）

借鉴 `tokc` 的三层计费模型，一个 skill 的 token 成本不是单一数字，而是三层、计费频率完全不同：

| 层 | 内容 | 计费时机 |
|---|---|---|
| T1 常驻税 | frontmatter 的 name + description | **每次请求、每个会话都发**（在系统提示的 skill 目录里）|
| T2 正文 | SKILL.md 的 body | 每次被调用时加载一次 |
| T3 按需 | references/、scripts/ | 只有真正读文件时才计 |

**关键洞察**：最该优化的是 T1 和 T2，不是看总量。
- T1 常驻税：description 每次都发，且有缓存系数（×5 级别）。一个 250 token 的 description 被重发 200 次，比 6000 token 的正文每月用 5 次还贵。→ description 必须精简。
- T2 正文：每次调用全量加载。正文大且高频复用 → 脚本化收益最高。

预测步骤：
1. 估 T1：description 字符数 ÷ 4，乘会话数（常驻，最贵）。
2. 估 T2：正文字符数 ÷ 4（中文 ÷ 2），乘预计调用次数。
3. 脚本化收益：把 T2 里的确定性逻辑外化成脚本后，T2 从「整段正文」降为「一句脚本命令 + 读结构化产出」，固定开销几十 token。
4. 结论：T1 冗长 → 先瘦 description；T2 大且高频 → 脚本化迁移。

**阈值参考**：description > 250 token 视为 T1 臃肿；正文 > 8000 字符且复用 ≥ 3 次视为值得脚本化。

### 4.2 定性质 + 反模式（script-first 架构）

借鉴 `script-first-skill-architecture`，判断哪些能脚本化：

- **该脚本化的**（确定性、会重复）：读文件、解析结构化格式、正则/关键词分类、计数归一化。→ 全部下沉到 `scripts/`，SKILL.md 只写「运行脚本 + 呈现 JSON」。
- **该留给 agent 的**（核心价值是判断力）：代码审查、架构分析、非结构化自然语言理解、需与用户协商的决策。

**三条反模式（必须避免）**：

1. **指令级优化**：只加「不要 grep 这些文件」而不给脚本替代。模型会绕到别的 token 昂贵的路径。要么给脚本，要么别优化。
2. **混合分类**：脚本分类一部分、模型分类一部分。这仍会加载上下文和参考文档。**全押脚本**，脚本分不了的就标「未分类」丢弃，不要交回模型。
3. **双重规则定义**：分类规则既在脚本里又在 SKILL.md 里。会漂移、模型可能覆盖脚本决定、浪费 token。**脚本是规则的唯一来源**。

**「脚本产出、模型呈现」是目标形态**：脚本做全部机械工作、输出预分类 JSON；SKILL.md 只指示「运行脚本、读 JSON、格式化呈现」，明确禁止重新解析/重新分类/加载参考文件。

### 4.3 申请（带数据，不带口号）

迁移脚本也是一个动作，先向用户申请，且**申请时带上 4.1 的量化预测**，而不是空喊「能省 token」：

> 检测到这个 skill 正文约 8500 字符（≈2000 token/次），预计会复用 ≥ 3 次。把扫描逻辑外化成一个本地脚本（如「扫描」脚本，命名按功能）后，每次调用可从 2000 token 降到约 50 token。是否迁移？

用户同意后才落盘脚本。

## 阶段五：使用后迭代判断

一个 skill 被使用后，判断是否需要迭代：

1. 收集事实：使用中是否报错、用户是否纠正、`skill-evaluator` 的 A/B 是否显示 dead weight 或 negative。
2. 命中任一 → 向用户申请迭代：
   > 检测到 `secret-scan` 在本次使用中【误报了 .env 的 PYTHONPATH 行】。建议迭代修正。是否生成 `SKILL_v2_draft.md`？（回复「同意」生成草案，回复「拒绝」跳过）
3. 迭代产物是**草案**（`_draft` 或 `v2`），绝不直接覆盖原文件。用户审查后才生效。

## 边界

- 不自动落地任何东西：建立/迁移/迭代都是申请，最终裁决权在用户。
- 触发判断的三个维度是启发式，阈值可调；宁漏报不打扰。
- 本 skill 与 `skill-evaluator` 分工：evaluator 负责「这个 skill 好不好用」（测量），本 skill 负责「什么时候该建/该改」（生命周期）。迭代判断时可调用 evaluator 拿数据。
