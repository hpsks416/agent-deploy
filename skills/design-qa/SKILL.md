# design-qa（去 AI 味设计评审）

把「设计品味」从「靠设计师眼光」拆成**可判定的评审条目**——评审 AI 生成的界面，找出「AI 味」（模板化外观），产出结构化报告 + 改法。

## 触发

- 用户要评审/优化一个 AI 生成的界面（网页/落地页/前端组件）。
- 用户问「这界面是不是 AI 做的 / 有没有机器味」。
- 批量产出页面后要统一「去味」。

## 评审动词（入口）

| 动词 | 语义 | 是否改写 |
|---|---|---|
| `audit` | 只读体检：逐条对照「AI 味清单」打分，只报告不改 | 否 |
| `critique` | 挑毛病：按严重度分级（critical/major/minor）列出问题 + 位置 | 否 |
| `polish` | 打磨：给每个问题一条具体的改法建议（不改原文） | 否 |
| `redesign` | 改写：在用户同意后按建议重做界面（保留功能，只动视觉） | 是（先申请） |

## 评审流程

1. **读界面**：拿到 HTML/CSS/组件代码，或对页面截图/描述。
2. **逐条体检**：对照 `references/ai-slop-patterns.md` 的可判定清单，逐条打「命中/未命中」。
3. **分级**：每个命中项标严重度（critical=一眼假 / major=明显模板感 / minor=细节瑕疵）。
4. **出报告**：结构化 findings（id + 严重度 + 位置 + 现象 + 改法），只报可判定的，不报「我觉得丑」。
5. **先申请后改写**：`redesign` 前先列改动清单让用户点批；`audit/critique/polish` 只读不改。

## 铁律

- **只报可判定信号**：命中/未命中基于清单的客观特征（字体名、色值、结构模式），不靠「我觉得丑」。
- **严重度需影响**：只有「用户一眼能认出是 AI 做的」才算 critical；主观偏好不算问题。
- **不越界**：只评视觉/排版/组件，不评业务逻辑、不改功能。
- **先申请后改写**：`redesign` 是改写，改动清单先让用户点批再动手。

## 文本模式（text）：给文字去 AI 味

界面之外，「AI 味」还有**文本层**。触发：用户要「去 AI 味 / humanize / 改得像人写的 / 太机器了」，对象是 README、文档、邮件、帖子、答复。

方法借 `ste80-humanizer`（MIT，Pass 1 的 26 条来自 Wikipedia「Signs of AI writing」+ blader/humanizer 目录；Pass 2 是 ASD-STE100 的 80% 版）。**两遍走**，逐条报编号。

### Pass 1：26 条 tell（命中就改；§1–§5 单次命中即改）

| § | tell | 改法 |
|---|---|---|
| 1 | 「不是 X，而是 Y」式对比 | 直接说结论；只有读者真信 X 时才保留对比 |
| 2 | 一行式收尾/碎片（「这才是关键」「无需配置」） | 删重复收尾，把碎片并入一句判断 |
| 3 | 听起来很深的话（「本质上是 X 的 Y」） | 换成具体主张 |
| 4 | 铺垫式开口（「让我们看看」「话说回来」） | 删掉，直接进正题 |
| 5 | 自设靶子（「需要说明的是，我并不是说…」） | 删掉防御性铺垫，除非上下文真有人反对 |
| 6 | 强行三连（「快、稳、可扩展」） | 含义真有三部分才保留三连 |
| 7 | 重复句式开头（「它读取…它检查…它启动…」） | 合并句或以动作开头 |
| 8 | 破折号成灾（—、–、` -- `） | 改句号/逗号/冒号/括号；代码与 URL 不动 |
| 9 | 限定词堆叠（could potentially…） | 只留一个限定词 |
| 10 | 连字符误用（well-documented 的位置） | 名词前加、名词后不加 |
| 11 | 被动/缺主语（「无需账户。数据已同步。」） | 点出施动者 |
| 12 | 套话词（delve/leverage/robust/seamless/crucial/pivotal/tapestry/testament…） | 换平实词 |
| 13 | 拔高意义（「里程碑」「长远遗产」） | 保留事实，停在一个具体事实上 |
| 14 | 含糊关联（associated with / linked to） | 写出原文给的关系，不许自己发明 |
| 15 | -ing 尾挂（highlighting/ensuring/fostering） | 除非原文支持，删掉 |
| 16 | 销售腔（groundbreaking/world-class/坐落于…） | 说它是什么、能做什么 |
| 17 | 借权威（专家认为/行业报告显示） | 指名道姓，否则删；绝不编来源 |
| 18 | 回避 is/are/has（serves as/stands as/boasts） | 就用 is/are/has |
| 19 | 装饰性加粗（每条一个「**标签**：」） | 去掉加粗；标签无信息就把列表改成散文 |
| 20 | 装饰性标题（Title Case、emoji、箭头） | 句首大写，标题写清装什么 |
| 21 | 弯引号（“ ”） | 改直引号 |
| 22 | 聊天残留（Great question!/希望有帮助/需要我…吗） | 删外壳，留内容 |
| 23 | 知识边界猜测（截至我所知/可能始于…） | 说来源没显示什么，或删 |
| 24 | 标题在首句重复（「## 安全」后接「安全很重要」） | 删那句 |
| 25 | 关于文档的元话（「本表用于对比」「为替换…而加」） | 写主题，不写文档 |
| 26 | 对读者重讲已知（答复里重述问题与诊断） | 先给结论，只留读者缺的那一个事实 |

### Pass 2：结构（S1–S15 的 80% 版，摘要）

一句话一个意思；指令句 ≤20 词、描述句 ≤25 词；条件在前、命令在后；主动语态、点名施动者；简单时态（现在/过去/will/祈使）；动作放动词里（不写「做出决定」）；情态照实（can/must/will，保留原不确定度）；平实词、一词一义、不轮换同义词；三个名词以内；一段一个主题 ≤6 句；步骤与描述分开、警告放步骤前；不用分号。

### 保真铁律（比风格优先）

- **事实、数字、名字、日期、引号、标识符一个不能少**；§6/§9/§19 最容易弄丢事实。
- 不确定度照搬：「may」不能变「will」，「40+」不能变「约 40」。
- **不许加**新事实、例子、理由、来源；不许把词改得更含糊。
- **不碰**：代码、命令、路径、URL、版本号、错误信息、产品名、引文。
- 矛盾就并列保留，并在结尾标注。

### 什么时候不做

合同/法律/监管文本（只给平实摘要，不改写）；代码（只改注释与文档）；纯引用/标题/名字；诗、小说、演讲、段子、品牌文案（未经要求不做 Pass 2，STE 会删掉声音）；2022-11-30 之前的文本不是 AI 写的。

### 输出

改完的正文 + 一列编号化改动（如「§1、§8、S2」）+ 被删/不确定之处说明。可选用 `ste_check.py`（MIT，来自 ste80-humanizer，不放本仓）做启发式自查——它是启发式，不是 AI 检测器，也不能声称「符合 STE」。
