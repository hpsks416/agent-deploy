# METHOD：复杂/破坏性任务的正确执行方法

> 从「配置 DSH MOBILE → 升级 DSH → 连环踩坑」这一真实案例提炼出的**可复用执行方法**。不写复盘，只写「下次照着走」的流程。落点：框架的自我改进闭环 + 四道强制检查。

## 一句话方法

```
开场读画像 → 铁律一（三道检索）→ 编排分解 → 做事（四步强制检查）→ 铁律二（固化）→ 人类终审
```

## 逐层动作（8 层 → 该做什么 → 本次反例）

| 框架层 | 该做的动作 | 本次反例（未做 → 后果） |
|---|---|---|
| ② 画像层（开场） | 先读 `persona.md`，对齐「选项弹窗 / 前沿一手 / 判重读版本差异」 | 未读 → 用文字问、绕远路 |
| 铁律一 + ⑤ 检索层（动手前） | **三道检索**，不检索不动手 | 三处全跳过 → 误判方向 + 闪退 + 从零排查 |
| ④ 编排层 | 用 `agent-workflow-orchestration` 拆成有序步骤 + 门控 | 线性边做边修 → 两段长时间返工 |
| 做事层（用 skill） | 走对应 skill 的强制检查清单 | 只做了备份，漏了检索/文档/兼容矩阵 |
| 铁律二 + ③ skill 生命周期链（收尾） | 命中知识盲区 → 申请固化 → 分层 → 脚本化 → 人类终审 | 最后才固化，教训没提前沉淀 |
| ⑥ 安全发布层（若推送） | secret-scan → secure-push 强制检查 | 本次仅反馈 issue，不涉及推送 |

## 三道检索（铁律一强制检查，动手前必做）

任何「可能有现成方案」的任务，先回答三个问题：

1. **目标是什么？** —— 有无现成项目/工具（如「DSH MOBILE」→ `saya-ch/dsh-mobile` 插件+App，而非自以为是「浏览器访问」）。
2. **操作的已知坑？** —— 该操作（升级/迁移/改环境）有没有公开的坑清单（如「DSH 升级必须双处同步」）。
3. **同名报错的现成 issue？** —— 报错关键词丢进 issue/讨论区，往往早有人踩过（如「内测声明无法保存」→ deepseek-ai/deepseek-harness Discussion #860）。

> 检索类任务**默认走 `open-source-scout`**；仅非开源项目检索才退回 web_search。

## 四步强制检查（升级/迁移/改环境，缺一即停）

1. 检索已知坑与 issue；
2. 检索官方 README/文档的正确姿势；
3. 备份关键配置 + 明确回滚方案；
4. 确认版本兼容矩阵（如「全局 CLI 与 profile 双处同步」）。

> DSH 专属落地见 `dsh-upgrade-ops` skill；通用原则已并入 AGENTS.md 铁律一。

## 三条核心教训（本次为什么「越修越坏」）

1. **检索被当可选项**：三个「本应先搜」的节点全被跳过，直接上手。
2. **画像没在开场读**：「选项弹窗」早写在 persona.md 和铁律二里，却未执行 → 用户反复文字纠正。
3. **强制检查没落地成 checklist**：升级类操作没有「四步前置检查」可依，只能边做边补。

## 落地物对照（框架已固化）

| 教训 | 落地到 |

| 检索=强制检查 + 升级四步检查 | AGENTS.md 铁律一 |

**核心一句话**：框架的价值不在「事后复盘」，而在「事前门控」——把每一次踩坑都变成下一次动手前必须先过的检查项。
